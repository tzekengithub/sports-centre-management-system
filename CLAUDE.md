# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Sports Centre Management System: a university group assignment (AMCS1034 Software Development Fundamentals). It's a Python tkinter desktop app with four modules, and each module is written and graded per author (see `README.txt` §5). Code is marked against a fixed rubric of 16 criteria × 4 modules (`Report Support/RUBRIC_CHECK.md`), so every module file must keep showing each criterion on its own.

## Commands

```
cd "Source Code"
python main.py                      # run the app (Python 3.10+ required: uses match)
python -m py_compile *.py           # compile-check every file
grep -nE "lambda |\[.* for .* in .*\]" *.py   # forbidden-syntax scan, must return nothing
```

There's no test framework. Tests are throwaway scripts that import the logic functions directly (`import membership; membership.register_member(...)`). Delete them afterward and put `data/*.txt` back to the clean sample state. The simplest reset is to delete `Source Code/data/`; the next run recreates it with fresh sample rows dated relative to today. Record executed cases in `Report Support/TEST_CASES.md`.

## Syllabus constraints (hard rules)

- **Standard library only, from a whitelist:** `tkinter`, `tkinter.messagebox`, `datetime`, `os`, `sys`. No `ttk`, no `calendar` (`common.days_in_month` exists to avoid it), and no other imports.
- **No lambdas and no comprehensions.** Use named nested functions for tkinter `command=` callbacks (see `make_day_command` in `common.py`) and plain `for` loops.
- **Each module file must show everything below on its own:** if/elif and `match`, `for` and `while` loops (the while loops are the `find_*_by_id` linear searches), a set, tuple and dict, a recursive function that the GUI actually calls (`count_*_recursive` / `total_*_recursive`), a class with private `__attr` plus getters/setters, inheritance (`Member`/`Coach` → `common.Person`, `Booking`/`SportsClass` → `common.Record`, `RetailBill` → `Bill`), a predefined module used directly (`datetime` / `os`, not only through `common`), and try/except. Don't remove any of these. Don't add dead code just to satisfy the rubric either: graders check that it's wired to a button.
- **Comment style:** a header docstring in every file (Module / `Member N: name (student ID)` / Purpose / Date; the assignment guide asks for the member line, and the student IDs are still blanks to fill in), a one-line docstring on every function, and `#` comments on non-obvious logic.
- **`main.py` must stay parseable on old Python.** It checks the version *before* importing the other modules and contains no `match` statement itself.

## Architecture

- **`common.py`** is shared by every module. It holds absolute data paths built from `__file__` (so the app runs from any cwd), domain constants (`SPORTS` courts/rates, `MEMBERSHIP_FEES`, `MEMBER_DISCOUNT_PCT`, opening hours, statuses), GUI style constants, file I/O helpers, `generate_id`, validators, the `open_date_picker` pop-up and the `Person` base class. Every module styles its window from the constants here.
- **Each module file has two layers.** The top half is pure logic: the class, `line_to_X`/`load_all_X`, and CRUD functions that `raise ValueError` on bad input. The bottom half is `build_X_tab(parent)`, which builds the module into a `tk.Frame`, catches `ValueError` and `OSError` (a data file that can't be saved) in each handler and shows it through `messagebox`.
- **Every tab opens on an action menu, with one page per action.** This is the user's explicit design: the tab asks "What would you like to do?", and each action (Register, Book a Court, Pay Bill…) is its own simple page with one main button. `common.build_action_menu(window, title, [(name, menu_hint, page_instructions), ...])` returns `(page_frames, page_hooks)`. Build each page into `page_frames[name]`, and put its refresh function in `page_hooks[name]` (it runs whenever the page opens). Most actions use `common.build_pick_page(...)`, which shows a list on the left and the picked record's details plus ONE button on the right. The module supplies `load_rows(search_text)`, `describe(id)` and `action_function(id)` (which returns a message or raises `ValueError`), plus an optional form, confirm text and summary line. Form or picture pages (Register, Create Bill, Book a Court, Hours & Commission, Daily Revenue) have their own `build_..._page`. Clicking the current tab again rebuilds it, which goes back to the menu. Add/update/delete for one record type is ONE page (the user's preferred pattern), built with `common.build_manage_page`: a blank form adds, clicking a row loads it for update, and a Delete button sits beside each row. Rows are widgets in `common.build_scroll_area`, because a Listbox can't hold buttons. It's used by Manage Coaches, Manage Classes and Manage Members; Members has no add mode, because Register has its own card page. Each action list follows the assignment guideline's purpose for that module: Booking is a courts × hours grid; Membership is registration by type; Coaching assigns coaches to private/group classes and tracks hours and commission; Billing produces daily revenue split by court/coaching/retail/membership. Use the shared widgets in `common` (`make_button`, `make_card`, `make_option_menu`/`set_option_menu_choices`, `build_list_panel`, `add_form_row`).
- **Dark mode / theming.** Never hard-code a colour. Use the palette names in `common` (`APP_BG`, `PANEL_BG`, `TEXT_COLOR`, `ACCENT_COLOR`, `BUTTON_COLOR`, `PAST_COLOR`, …). `common.apply_theme` reassigns them, and `main.py` then calls `common.recolour_widgets(root, old, new)`, which changes every existing widget's colours IN PLACE (nothing is rebuilt, so the current tab, page, typed text and selections stay). It maps old palette values to new ones, separately for background and text options (white is both a panel background and button text). So: never store a colour in a variable that outlives a toggle (store a role such as `is_past` instead, see `build_manage_page`), don't use `ACCENT_COLOR` as a fill (it is ambiguous with `BUTTON_COLOR` in light mode), and re-read palette names when you need them (as `switch_to_tab` does). Read colours when a widget is built, not at import time (e.g. not `X = common.APP_BG` at module level). `ACCENT_COLOR` is a *text* colour (light green in dark mode); use `BUTTON_COLOR` for filled backgrounds. Options the code doesn't set come from `common.apply_widget_defaults` (the tkinter option database). The theme is saved in `data/settings.txt`.
- **The Home header is the one exception to the colour rules.** It is drawn on `tk.Canvas` widgets in `main.py` (`HomeHeader`, `PillButton`), which `recolour_widgets` can't reach item by item, so it has its own `HEADER_PALETTE` (dark and light) and `main.on_theme_toggle` calls `home_header_state["header"].apply_theme()` after recolouring. The page colour still comes from `common.APP_BG`. The clock uses `datetime`, not `time`. A theme toggle must leave the same number of canvas items (no leftovers); the clock only changes item text each second (`itemconfig`), it never redraws.
- **Status colours.** `common.status_colours(kind)` gives (background, text) for `'good'` (green, `FREE_COLOR`), `'bad'` (red, `BOOKED_COLOR`), `'warn'` (amber, `SELECTED_COLOR`), `'info'` (blue, `INFO_COLOR`) and `'quiet'` (grey, `PAST_COLOR`). `build_pick_page` rows may be `(id, text, kind)` to colour that list row (Listbox `itemconfig`, which `recolour_widgets` also remaps), and `badges=function(row_id)` returns `[(text, kind), ...]` shown as coloured badge labels above the details (Booking pages: CONFIRMED/CANCELLED, UPCOMING/STARTED, NOT BILLED/UNPAID/PAID). Use these for new status colours instead of hard-coding.
- **Every interactive widget needs a hover hint and every number needs a unit** (user requirement). Pass `tip=` to `make_button`/`make_entry`/`make_option_menu`/`add_form_row`, or call `common.add_tooltip(widget, text)` for raw widgets (radio buttons, grid cells, labels bound to clicks). Hints should say what to do and what format to type, e.g. "A number from 1 to 500, e.g. 60". Show money as RM, times as HH:00, and durations in hours.
- **Number input** from the GUI goes through `common.parse_decimal` / `parse_whole_number`. They give friendly messages, reject nan and inf (`float()` accepts both), and cap the range. Logic-layer checks are written as `not (low <= x <= high)` so nan fails them too.
- **One window, tabs.** `main.py` builds a single `Tk` with a tab bar of plain `tk.Button`s (no `ttk.Notebook`, since it's off the syllabus) above a content frame. `switch_to_tab` destroys the current tab's frame and rebuilds the chosen one with `if/elif`, so every switch reloads fresh data and clears half-typed input. Modules must never open their own `Toplevel` for the main UI. Anything that needs a real window must use `widget.winfo_toplevel()`: `transient` owners (see `common.open_date_picker`) and key bindings (see Membership's Enter key, which is guarded with `winfo_exists()`).
- **Storage is pipe-delimited `.txt`, one record per line**, in `Source Code/data/`. There's no in-memory cache. Every operation re-reads the file through `common.read_lines`, then writes it back with `common.rewrite_records(file, lines, line_to_X)` (update/delete) or `append_line` (create). Loaders use `common.split_fields(line, n)` and skip malformed lines; `rewrite_records` puts those unreadable lines back at the end so an update never erases them. Files are read as `utf-8-sig` (`READ_ENCODING`) so a Notepad BOM is ignored. Dates are saved through `common.normalize_date` (always `YYYY-MM-DD`), because clash checks and searches compare the raw text. Free text must go through `common.contains_forbidden_character` (it rejects `|` and `;`), because class participants are stored as a `;`-joined list (`MEM001;MEM003`). Receipts are written one per payment to `data/receipts/`.
- **IDs:** `PREFIX###` (MEM, BKG, CCH, CLS, BIL). Each new ID is one more than the highest suffix in the file *or* the highest ever used, kept in `data/id_counters.txt` (`append_line` updates it via `note_used_id`). So an ID is never reused after a delete. `remember_highest_ids` also learns the IDs already in every file at start-up and before every `rewrite_records`, so sample or hand-typed IDs are covered too. `append_line` saves the counter *before* the record, so a failed counter write can't leave a saved record behind.
- **Lists and details panels:** cut long text in list rows with `common.fit_text(text, width)` (ends in …). Details panels use `common.details_text([(label, value), ...])`, which gives aligned `Label:  value` lines in `MONO_FONT`. List headers name the ID column ("Class ID", "Member ID"), not just "ID".
- **Drop-downs that list members or coaches** use `common.make_filtered_menu` (a search-as-you-type combo box: an Entry, a ▼ arrow button that lists everyone, and a pop-up Listbox placed on the toplevel; no Toplevel/ttk). The pop-up opens upward when there is no room below the box (Book a Court's member box is at the bottom of the page), shifts left near the right edge, and shows fewer rows in a very short window, so it is never cut off by the window. It returns `(holder, entry, set_choices)` (`stacked` is ignored). Typing searches the full text, but the box shows (and the variable holds) each choice cut with `fit_text(choice, width)`, so pages must key their lookup dicts with `fit_text` too. Nothing is picked until the user picks: the menu starts on `common.CHOOSE_TEXT`. Manage-page rows may be `(id, text, "past")` to show them greyed out. A `save_action` returning `None` means the user cancelled (nothing saved, no message). `open_date_picker(..., allow_past=False)` greys out past days; it opens on the month typed in the box. The window is 1000 px wide: check new pages fit (the right-hand card is packed before the list, so only the list shrinks).
- **Recursion limit:** the rubric's recursive totals are called through wrappers (`count_members`, `total_bills`, `total_commission`) that switch to a loop above `common.RECURSION_SAFE_LIMIT` (500).
- **Modules read each other's data files directly, not each other's Python functions.** `membership` reads bookings/bills to block deleting a member with a future CONFIRMED booking or an UNPAID bill. `coaching` reads members when enrolling. `billing` reads members (for the discount %), bookings and classes to build a bill. If you change a record format, every reader in every module has to change too.
- **Record field orders** are defined by each class's `to_line()`. The sample rows in `common.build_sample_rows` show each one.
- **Business rules to keep:**
  - Booking clashes are detected with set intersection of hours, and only CONFIRMED bookings count.
  - Daily revenue counts PAID bills only.
  - Cancelling a booking deliberately leaves its bill untouched, because refunds aren't in the syllabus.
  - Bookings are never deleted (user requirement): a cancel sets status CANCELLED and the record stays. Only VOID bills can be deleted.
  - Booking has 4 actions: Book a Court (+ Save Day Sheet), Reschedule Booking, Cancel a Booking, View All Bookings. Cancel can cancel just some hours (`cancel_booking_hours`, Cancel from / Cancel until): the original ID keeps only the cancelled hours as CANCELLED and the hours before/after become new CONFIRMED bookings, in one write. A booking that has started (`booking_has_started`) or has a non-VOID bill (`booking_bill_id`) can't be cancelled or rescheduled. Reschedule keeps the length and sport. A member must be valid on the booking date. Book uses `grid_state["date"]`, never the raw date box.
  - Exit always asks first: the Exit tab and the window's X both go through `on_exit` in `main.py`.
  - Coaches have a status (ACTIVE/INACTIVE, 7th field; old 6-field lines load as ACTIVE). Delete removes a coach with no classes, refuses one with upcoming classes, makes one with only past classes INACTIVE so history stays, and for one who is already INACTIVE just says so (their history can't be deleted). Inactive coaches can't get new classes.
  - A class that has started is a record: it can't be edited, deleted, or have members added or removed (hours, pay and commission are worked out from it). A class can't be deleted while a non-VOID bill points at it (`coaching.class_bill_info`); a PAID bill can never be voided (`billing.void_bill`), so such a class (or booking) is kept for good and the message says so. A billed class keeps its fee and duration. Removing a member from a class is refused while a non-VOID bill exists for that member and class. Editing a class re-runs `member_enrol_problem` for every enrolled member when its date, start or duration changes. `coaching.line_to_class` range-checks what it loads (like `line_to_coach`), tidies the date, and returns None for impossible rows; `rewrite_records` keeps such rows in the file, just hidden. A member can't be deleted while enrolled in a class that hasn't started. Enrolling checks: class not started, membership valid on the class day, no overlapping class for that member (`member_enrol_problem`). A private session's member is saved inside the new class in the same write. Hours & Commission counts only classes that are over (`split_worked_classes`) and shows Pay = hours × hourly rate. Coach phone numbers must be unique (`coaching.coach_phone_in_use`). Changing a coach's sport also moves their upcoming classes to the new sport.
  - A booking or class can't be billed twice (`billing.billed_references`). Past dates can't be booked, scheduled or enrolled in, and a start hour that has already begun today is rejected too.
  - Names allow letters, spaces, `/` and `'` (`common.is_valid_name`). Capitalisation goes through `common.format_name`, never `str.title()`, which would give "Ch'Ng".
- **The Booking grid** has courts as rows and hours as columns. Clicking a free cell toggles it in `grid_state["picked"]` (a set of `(court, hour)`); any hours on any courts can be picked, and Book (`create_bookings`) saves each run of consecutive hours on a court as one booking, all-or-nothing. A click only recolours cells in place (`restyle_selection`), it doesn't redraw; past hours are grey. The grid redraws on Enter, on `<KeyRelease>` once the box holds a full 10-character valid date, and on `<FocusOut>`. Pack layout gotcha: pack a bottom bar with `side="bottom"` *before* any sibling that uses `expand=True`, or it gets zero space and silently never shows (check with `winfo_ismapped()`).

## Verifying GUI changes

Reading the code isn't enough: past bugs (a NameError when opening a window, an invisible button bar, a grid not redrawing for a typed date) only showed up when the window was actually launched. To check a change, patch `tk.Tk.mainloop` to run a test function and call `main.main()`. Then drive the buttons with `.invoke()` (monkey-patch `messagebox` so the dialogs don't block) and check visibility. `winfo_ismapped()` is false whenever the window is covered, minimised or the screen is off, which makes tests flaky. It's more reliable to treat a widget as shown when it and every ancestor up to the toplevel has a non-empty `winfo_manager()`. Screenshots come out black when the screen is off. Call `root.update()` before looking for widgets, since nothing is mapped until it runs. Menu button names are reused as page button names (e.g. "Register"), so pick the last mapped match. Each action module exposes its action list (`BOOKING_ACTIONS`, `MEMBERSHIP_ACTIONS`, `COACHING_ACTIONS`, `BILLING_ACTIONS`) for tests to loop over. `PIL.ImageGrab` is installed; screenshot the window to check layout.
